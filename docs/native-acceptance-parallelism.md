# Parallel Windows acceptance

The Windows acceptance workflow runs three independent producers for the same frozen source:

- `bulk-import-browser` retains every existing Rust protocol and real-browser scenario
- `windows-pure-checks` runs every original Windows Node test invocation, `npm test`, Cargo formatting/workspace tests/clippy, and the complete Python suite with the original locked dependencies and static-CRT flags
- `native-feature-acceptance` builds one release EXE and runs every existing native scenario serially with the original fresh-profile, source/EXE, fixture, ownership and evidence checks

The native path keeps the fast PowerShell parser and filename/fixture-ownership preflight. The pure-check path also runs these platform contracts. Cache restore/save remains optional acceleration on the build path; no cache entry or cache hit can satisfy an acceptance gate. The pure-check job does not share a writable target directory with the build job.

`native-package` requires successful completion of all three producers. A failed, skipped, canceled or missing producer suppresses candidate creation. Before downloading any native inputs, its join checks actual job results, every producer's mandatory-step gate, exact SHA/tree, workflow run and attempt, repository, both lockfile digests, installed Rust/Node/Python versions, and Windows static-CRT flags against the packaging checkout. The source explicitly pins Rust 1.99.0 and Node 22.23.3 on every producer, Windows Python 3.12.10 on pure/native/package, and Linux Python 3.12.14 on the browser producer. This intentional Python platform difference preserves the versions observed in native555 jobs 112372191556 (Windows) and 112372191781 (Linux), without downgrading Linux. Every identity retains the actual OS and full installed versions: each producer must match its declared platform pins, all Windows Python versions must match, and common Rust/Node/source/locks must match across all producers. Wrong OS, a swapped platform matrix or any unapproved patch fails closed. Retries must rerun all jobs: a partial rerun leaves earlier producer attempts and the join rejects mixed attempts. Each producer's final gate explicitly checks actual outcomes and conclusions, including default-success steps that GitHub could otherwise skip. Optional cache operations are excluded; existing always-running failure-evidence behavior is preserved.

Each existing bounded JSON diagnostic pair becomes available immediately after its complete evidence root's final producer or recheck, including failed scenarios. This covers bulk import, VSQ song, performance, pitch bend, authoring, VSQ authoring and canonical practice in both environments, plus native desktop and browser pack management. Authoring roots wait for their native protocol and all hosted sizes; canonical browser evidence waits for its protocol, both sizes and both rechecks. Native Basic JSON/PNG diagnostics also follow their owner; exact VSQ seed/restart PNG diagnostics keep their existing position. Every existing filename, step ID, `always()` condition, byte bound and mandatory producer gate remains. Later independent scenarios continue under their existing prerequisites, and complete evidence artifacts still upload at the end. These small artifacts remain diagnostic subsets and cannot establish acceptance.

The build-diagnostics phase has an additional `build-diagnostics-windows-diagnostics-${sha}` artifact immediately after its independent recheck. It uses the existing bounded JSON/PNG collector with an explicit build-diagnostics scope. It retains unchanged generated root reports, all available action/result pairs and PNGs within the existing 32-action host limit, including the original 13-click success sequence, profile-creation proof and snapshots. Its hashed inventory includes the source SHA and presence/empty-state records for the named Scores directories; directory records survive artifact transport without inventing missing directories or uploading library contents. WebView profiles, private files, logs and the EXE are excluded from this small artifact. Payload plus inventory must fit 23 MiB, leaving room below the 24 MiB delivery limit; overflow fails visibly without truncating or recompressing originals. Missing or partial producer evidence remains explicitly diagnostic-only. The unchanged full native artifact and native transfer still retain their original authority and mandatory package re-verification.

The final `acceptance-summary` always runs and has no checkout or artifact-download dependency. It requires all four jobs, their mandatory-step gates, original feature outcomes, matching identities and immutable candidate/delivery artifact IDs and digests. Full **Verify WorldMusicClub** for that exact SHA remains separately required before delivery or promotion. A native candidate or a successful transfer is not checkpoint acceptance.

## Transferring the original proof

The native producer uploads one bounded `native-inputs.zip`. Packaging downloads only the immutable artifact ID exported by that producer in this run. It checks the ZIP SHA-256 against the producer's independent job output, then verifies every retained file hash and size, exact manifest membership, required roots, safe paths and fresh destinations. Automatic artifact-action digest warnings are not used as acceptance.

The transfer includes the exact EXE, original build provenance, generated license inputs/notices, and the existing scenario JSON, PNG, logs, downloads, original fixtures, Scores payloads and required empty directories. WebView profiles, dependencies, caches, arbitrary source files and credentials are excluded. Bounds are 16,384 files, 4,096 directories, 1 GiB total, 32 MiB per ordinary file, 256 MiB for the EXE and 4 MiB for the manifest. Symlinks, junctions, hard-linked evidence/notices, unsafe Windows names, case aliases, duplicate/archive-only members, compressed nested members, changed bytes and tracked/occupied destinations fail before restoration.

Cargo may hard-link its top-level release EXE from its own deps directory. Only that exact producer EXE permits multiple links while reading; repeated bounded hashes bind an independent regular ZIP copy, and restoration creates a fresh ordinary EXE. Link metadata is never transferred.

Original evidence bytes, absolute native paths, PID/HWND observations, profile relationships and screenshots are never rewritten. The consumer must have the same absolute workspace and runner-temp layout; a different runner layout fails closed and needs investigation. No historical process observation is treated as a live process on the second runner. Existing semantic verifiers run again before packaging.

The producer captures `native-build-provenance.json` on its own VM, binding source metadata, run attempt, producer job and exact EXE. The package preserves those original bytes and original `build_platform`; separate `packaging_environment` fields describe the packaging VM. The runtime delivery record distinguishes the original build from packaging and actual normal startup. Both extracted full and runtime packages still undergo their existing real Windows normal-startup checks. Existing same-runner manifest callers remain compatible; the new split workflow requires the provenance input.

## Verification and rollout

Local unit/contract tests exercise failed, skipped and missing producers; mismatched SHA/tree/run/attempt/locks/tools/CRT; tampered or unsafe transfer inputs; missing evidence; changed EXEs; altered original build provenance; and suppressed workflow dependencies. Linux-only verification cannot establish Windows GUI success, Windows junction behavior, real cross-runner restore compatibility or elapsed-time savings.

Observed completed native554 Windows validation took 57m24s; Node checks took 8m26s, Cargo workspace tests 10m14s, clippy 1m59s and Python tests 1m55s. These identify roughly 21–23 minutes of serial checks that can overlap build/UI work. This is an opportunity estimate, not a measured speedup. The [completed native554 job](https://github.com/Goldgom/WorldMusicClub/actions/runs/37486927311/job/112349262895) and [native545 job](https://github.com/Goldgom/WorldMusicClub/actions/runs/37457277080/job/112247846421) both missed the build cache. A workflow edit changes the existing cache key, so a cold cache is expected. Additional Windows queue/setup cost, transfer/upload time and runner availability can reduce or erase the estimate.

Keep frozen555 unchanged. Measure end-to-end queue, setup, checks, build/UI, transfer and packaging times only in a later substantive frozen validation batch, and require a real second-runner restore plus existing `--check` and ordinary-startup results before reporting a benefit. No run is started by this change.

To restore the prior CI topology, revert this whole cohesive change, including its workflow, transport/provenance helpers and contract-test migrations. Do not restore only the workflow or remove the package join while leaving pure checks independent: that would reintroduce candidate creation after a pure-check failure. Keep historical artifacts and frozen branches intact.
