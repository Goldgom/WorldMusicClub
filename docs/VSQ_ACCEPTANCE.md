# VSQ consumer acceptance

These checks use only the committed original semantic fixtures generated by
`crates/desktop-shell/examples/generate_vsq_fixture.rs`. They never take external
or private music paths. Metadata and authoring score bytes, including the integer
9007199254740993, are copied into the chooser ZIP without JSON reserialization.

## Local protocol and verifier checks

- `node --test tests/native-vsq-song-evidence.test.js` checks original fixtures,
  strict evidence rejection, native timing boundaries, exact exported target
  identity, and bounded stdio failure/shutdown. Its synthetic reports and PNGs
  are verifier inputs, never evidence of actual Windows/browser acceptance.
- `WMH_NATIVE_IMPORT_DRIVER=<exact-source driver> node scripts/check-vsq-song-native.mjs`
  runs actual Rust over stdin, including both declared-tail and written-padding
  variants, explicit runtime choice, forbidden vocal mode, exact JSON export,
  reimport, and new-process load. It opens no listener, browser, or native window.

## Hosted browser and Windows

`hosted-vsq-song-check.mjs` refuses to launch unless GitHub Actions and the hosted
browser permission are present and `WMH_SOURCE_SHA` matches checkout HEAD. The
workflows run it at both 1280×720 and 1280×900. It uses real Chromium controls,
chooser downloads, and AudioContext calls with an actual exact-source Rust stdio
adapter. Application APIs are not mocked. A separate fresh profile and Rust
process perform the restart phase at each viewport. These runs do not establish
native Windows acceptance.

The `vsq-song` scenario in `windows-desktop-acceptance.ps1` runs the same renderer
scenario in two real Windows processes with independently fresh WebView profiles
and the same test-owned native Scores folder. The existing OS chooser ownership,
foreground hit, finite fixture allowlist, normal close, no-listener checks and
file snapshots remain required. Every action uses the actual client geometry;
controls must scroll into the viewport and pass a center-point occlusion check.
All action screenshots remain in evidence, including English and Chinese choices.

The scenario requires a chooser preflight reporting every original track, a
saved `playable:false` selection, visibly unavailable full vocal mode, explicit
base-note choice without automatic audio, real reference scheduling, and actual
frame observations matching the native note and written-measure intervals. It
checks native PreMeasure, note-off gap, and the source-declared unwritten tail.
Practice must silence the human part, grade that native target only, keep machine
accompaniment out of input evidence, and capture one trusted keyboard onset.
Pause, navigation, reload and fresh-process choice reset remain separate checks.

Each operation has a distinct diagnostic stage and finite timeout. Native stdio
requests have a 10-second bound and owned-process shutdown has a 5-second bound;
an expired request terminates that test-owned driver. The renderer retains at
most 512 following rows, 128 API/control observations, 64 native actions, and a
1 MiB report. The verifier rejects absent observations, timing/identity drift,
synthetic input, bad chooser ownership, missing screenshots, and changes in the
exact primary/backup JSON or retained original ZIP.

Windows packaging reruns `verify-native-vsq-song-evidence.mjs --check` and binds
the resulting source SHA, tree and executable SHA-256 to the package before
copying its proof. Existing MIDI, media, bulk-import, folder, full-test, source
cleanliness and extracted-package startup gates remain unchanged. The exact
`/desktop-vsq-song/` output directory is ignored; similarly named source files
remain visible to the source guard.

Adding or passing local checks does not establish hosted or native acceptance.
No original vocal, voicebank, acoustic fidelity, audibility, latency or hardware
claim is made. Full vocal rendering remains unavailable.
